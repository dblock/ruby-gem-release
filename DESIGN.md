# Design

`Package::RubyGem` owns package construction and verification, `Destination::RubyGems` owns registry checks and uploads, `SourceControl::Git` owns Git operations, and `Hosting::GitHubRelease` creates hosted releases. Commands use argument arrays. The publication callback commits, builds once, tags, publishes to the configured registry, pushes the commit and tag atomically, and creates the optional hosted release with the verified exact artifact. The workflow retains setup, context checks, validation, destination-specific authentication, artifact uploading, and phase invocation. Release callbacks receive execution contexts; domain operations receive immutable release values.

`ruby-gem-release` supplies a reusable GitHub Actions workflow invoked with `workflow_call`, a step-based composite action, and a Ruby gem with shared lifecycle Rake tasks and objects for reading, setting, and incrementing numeric versions.

The shared workflow will orchestrate an end-to-end release: authorize the release, validate the requested version, invoke project-configurable preparation and next development iteration commands, run validation, build and preserve the exact gem artifact, publish with RubyGems Trusted Publishing, push the release commit and tag atomically, and create a GitHub Release. Project-specific changelog and version conventions remain in the calling repository.

The Rake tasks update exactly one constant assignment without evaluating the version file. The reusable workflow is the primary GitHub interface; a composite action offers the same release lifecycle as a caller-owned job step. Caller-provided shell commands run with the workflow's privileges and must be trusted.

Optional Ruby callbacks receive a frozen `ExecutionContext` containing an immutable `Release`, current step, observed step snapshots, configured workflow reference, and selected run metadata. Domain operations still receive only `Release`. The failure callback receives an immutable `ReleaseFailure` with the failed Actions phase, the captured Ruby exception when available, and execution context whose release can be absent; errors from the failure callback do not hide the failed job result. The workflow reads the initial and prepared versions from the gemspec and retains its previous version and configured calendar date across both phases. The optional `timezone` input defaults to UTC and sets `TZ` for date capture and Git timestamp offsets; identifiers are validated against the supported runner's `/usr/share/zoneinfo` files. Service-generated publication timestamps are unchanged. The optional version input selects the release version; standard preparation calls the configured version object's `set!` method inside the trusted staging boundary before updating the changelog. Custom callbacks receive the selected version and own their file updates; resolution verifies that the prepared gemspec honors the selection. The initial version is always retained independently. Callbacks own their version objects with no task-level strategy configuration; `with_version` and `with_next_version` return new release values without mutating the originals. Version objects own their file updates; optional changelog objects support `Intridea` and Keep a Changelog formats, including standard version comparison reference links. The caller chooses its objects and owns custom formats and unsupported links; callback failures stop the workflow.

`ExecutionContext` is provider-neutral and does not read GitHub environment values. `ExecutionProvider` supplies execution-platform services independently of registry destinations and release hosting. Its GitHub implementation owns Actions environment and output transport, ref and temporary-directory discovery, bot identity, step identification, secret masking, and OIDC token acquisition. Automatic selection uses it when `GITHUB_ACTIONS=true`; explicit `provider:` injection on workflows or tasks overrides detection. The base updates the current environment and retains outputs in process, using logical task IDs without observed history or run metadata. It does not implement external pipeline orchestration or identity-token acquisition.

Providers construct immutable execution contexts; contexts remain data snapshots rather than platform clients. GitHub contexts own step parsing and run metadata, reused by failure-phase selection. Environment capture exports the provider's storage location as `RELEASE_DIRECTORY`; package and Git operations use this neutral name or explicit directories rather than reading Actions variables. GitHub bot defaults are retained only in the GitHub provider. Another execution platform needs its own adapter and pipeline, not new package or Git implementations. No GitLab implementation is included.

Actions supplies the enclosing step ID explicitly, including for custom commands invoking multiple tasks, and a snapshot of prior visible step results. The GitHub subclass keeps outcome and conclusion distinct; absent steps are unknown, not skipped. Only supported public outputs are retained. Run metadata excludes credentials and the full event payload. The configured Ruby workflow is reconstructed through the Rakefile in each process, never serialized. Environment capture creates a unique private versioned state file outside the checkout; atomic writes persist only explicitly supported callback data, initially the next development version after a successful bump. Local callbacks share process-local state when no file is supplied. Step history does not track operations inside publication.

Changelog updates use `Commonmarker` to identify top-level headings and exclude code, HTML, and quoted blocks. Updates edit the original source rather than rendering the parsed document again, preserving unrelated Markdown formatting. Reference definitions are not exposed as separate parser nodes, so comparison references use source-level matching outside those excluded blocks, with parser validation that each reference is defined.

The `release:validate` decision step runs after context capture and before edits. Its optional callback returns exactly `true` to proceed or `false` to skip successfully; exceptions fail the release. Standard validation uses the read-only changelog `pending?` predicate or proceeds when the changelog is disabled, and a constructor `validate:` callback can replace that decision. Empty pending notes skip without downstream release operations or result callbacks. Both Actions interfaces validate the explicit `proceed` output, gate later steps, expose `skipped`, and record successful skips in the job summary. The former post-preparation `validate` command input is renamed to `test`.

Both built-in changelog formats reject empty release sections on direct `release!` calls before writing any updates. Markdown parsing distinguishes actual text and code from category headings, HTML comments or blocks, and reference definitions; `Intridea` removes its contribution placeholder before checking. The section ends at the next equal or shallower heading so historical notes cannot satisfy the guard. The same parsing supports read-only pending-note checks, with malformed headings, references, or placeholders raising errors rather than skipping. Projects supplying custom changelog implementations must implement `pending?` or provide their own validation decision.

The package builds once and publishes before atomically pushing its commit and tag. Git checks concurrency before publication and again before pushing. This leaves an unavoidable recovery window if the push fails after publication; see [RELEASING.md](RELEASING.md). The artifact-upload step runs even when publication fails, preserving the gem, digest manifest, and recovery bundle where available. Because building and publication now share a callback, Actions uploads recovery artifacts afterward rather than beforehand; runner loss during that callback can still lose the local files. Pull-request integration builds and installs the gem and executes both interfaces' callback commands in real consumers. Only package uploads and hosted-release creation are isolated; Git pushes use local bare repositories. These checks do not execute live Actions authentication or artifact uploading.

## Class Areas

Namespaces group implementations by responsibility: `Package::RubyGem` builds and verifies gems, `Destination` defines the package registry contract with a `RubyGems` implementation, `SourceControl::Git` manages commits and tags independently of hosting, and `Hosting::GitHubRelease` creates hosted releases. `Version` and `Changelog` retain their existing areas; `Release`, `ExecutionContext`, and `Tasks` provide domain values, execution snapshots, and callback registration. `ExecutionProvider` owns execution services, `Workflow::Environment` performs release checks through that provider, `Workflow::State` persists supported callback data, and `Workflow::RubyGem` installs the standard sequence. Class, documentation, and spec paths mirror namespaces.

Each workflow selects one registry destination independently of the package builder and optional hosting. The same package and destination are supplied to prepared-version resolution and publication, including manual task installation. Destinations own availability checks and exact-artifact uploads. Their authentication request selects existing RubyGems Trusted Publishing or preconfigured credentials; custom destinations do not silently contact RubyGems. Registry publication precedes the Git push, while hosted release creation follows it. No additional registry implementation or multi-destination orchestration is included.

Future hosting implementations can implement `publish!(release, package:)` without changing callbacks or Git operations. No shared hosting base or additional provider is implemented until real shared behavior requires one.

## Standard Workflow

Context capture enforces a clean checkout after dependency installation in both Actions interfaces. Preparation stages literal changed paths and records the exact index tree before testing, including outputs of custom preparation commands; publication never stages files and rejects any later non-ignored working tree or index changes. The standard next development iteration wraps version and changelog edits in the same preparation boundary, preserving custom version side effects such as README updates. Custom callbacks can use `Git#stage_changes!` around their trusted edits without requiring hard-coded version or changelog paths.

Prepared-version resolution checks the selected package's name and version at the configured destination before testing and authentication. The standard publication callback repeats that check before its release commit. The RubyGems destination checks the built artifact's actual name and version before uploading, without consulting an edited gemspec. HTTP 200 rejects a published version; only 404 permits proceeding. Unexpected statuses and connection failures stop the release, with bounded timeouts and no automatic retries. Custom callbacks can invoke `destination.check_version!(name: package.name, version: version)` before preparation or committing. The lookup is not a reservation and cannot eliminate races with other publishers; the registry remains authoritative.

`Workflow::RubyGem` installs the existing callback sequence using explicit version and changelog objects. Package, destination, Git, hosting, and execution-provider objects can be replaced independently without changing ordering. Only unambiguous gemspec, repository, branch, and artifact-directory defaults are used; version files and changelog formats are never guessed. An explicit `nil` disables changelog or hosted-release work, not package publication or version incrementing. Custom sequences continue to use `Tasks.install`; no general-purpose workflow framework is introduced.

## Composite Action

The root `action.yml` is the single Marketplace action metadata file. It invokes the same Ruby lifecycle tasks, authentication paths, and exact-artifact publication as the reusable workflow. Its input configuration uses `Workflow::Environment` to validate and export values across composite steps before preparation. Callers own job permissions, runner, environment, and concurrency; the reusable workflow continues to provide those settings without changing existing consumers.

Both YAML interfaces keep thin orchestration wrappers over the Ruby implementation. The reusable workflow deliberately does not reference a moving composite-action branch or a future release tag: a pinned workflow must remain independent of later action versions. Real consumer CI exercises both interfaces and verifies recovery artifacts and skipped iteration preparation after a failed action callback. Both interfaces use the same release versions, and published tags remain immutable.

## Project Release Caller

The project's `publish.yml` caller invokes the local reusable workflow through manual dispatch only, using the standard workflow configured in the root Rakefile and the Ruby 4.0 runtime already used by package CI. Every dispatch requests publication and requires prior release authorization; empty pending notes skip successfully. The caller grants only contents-write and OIDC-token permissions needed for release operations. Trusted Publishing setup remains a separate prerequisite.

The root Rakefile uses the project-local `ReleaseVersion` subclass of `Version::RubyConstant`. Its `increment!` updates README action and reusable-workflow references to the version just released while returning the version for the next development iteration. README edits are committed with the next development iteration, not the already-created release tag. The shared workflow and gem API remain unchanged.

### Owner-Bound Authentication

First publication with a pending trusted publisher requires the RubyGems account ID in the OIDC exchange. `Workflow::RubyGemsCredentials` requests an audience-bound identity token from its execution provider, then performs only the registry exchange through Ruby's standard HTTP and JSON libraries. It delegates masking and credential exports to the same provider and makes no retry or persistent credential-file writes. Only the GitHub provider reads Actions OIDC variables and emits Actions logging commands. The optional `rubygems-owner` input selects this helper; an empty input retains the pinned credentials action for existing gems. The project's caller reads the account ID from the non-secret `RUBYGEMS_OWNER_ID` repository variable.

## Logo

The logo in `assets/logo.png` is an original AI-generated image of a ruby gemstone launching like a rocket. This is the original generated asset; no editable source was provided. To create a replacement, generate a centered, text-free, red faceted ruby with an upward launch motif and a transparent background. Generation is not deterministic, so a replacement will differ. Preserve the original asset and inspect the full-size image and its 160-pixel README rendering for legibility and clipping when updating it.
